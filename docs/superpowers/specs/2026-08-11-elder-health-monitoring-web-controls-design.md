# 老人健康监测、佩戴状态与 Web 快捷控制设计

**日期：** 2026-08-11
**项目：** silver-care-iot
**状态：** 规划中
**适用范围：** Web 管理端、设备 TCP 网关、健康/位置数据、疑似跌倒事件

---

## 1. 背景

项目当前已经具备以下基础能力：

- 手表通过 TCP 长连接接入后端；
- 后端能够解析并保存 `LK`、`UD`、`UD2`、`AL`、`btemp2`、`bphrt`；
- Web 管理端能够查看设备、健康记录和位置记录；
- Web 管理端可以手工输入协议内容并向在线设备发送命令；
- 小程序能够查看最新健康数据、位置记录和疑似跌倒事件。

现有 Web 指令下发只返回“数据已经写入 TCP 连接”，无法说明：

- 手表是否收到并确认命令；
- 手表是否执行了命令；
- 立即定位后是否产生了新位置；
- 立即健康检测后是否产生了新的有效健康数据；
- 失败、超时或设备离线时如何处理。

本次规划将底层手写命令封装为用户友好的快捷操作，同时补齐佩戴状态、定时监测、健康数据有效性和跌倒事件闭环。

---

## 2. 目标

### 2.1 用户目标

Web 设备详情页提供清晰的操作按钮：

- 立即定位；
- 测量心率；
- 测量体温；
- 立即健康检测（组合执行心率和体温，可在真机验证后开放）；
- 刷新当前数据；
- 配置定时位置和健康监测策略；
- 查看命令执行进度和失败原因；
- 保留高级手写命令入口。

### 2.2 业务目标

形成以下闭环：

```text
用户发起操作
→ 后端检查设备状态和佩戴状态
→ 后端生成并发送协议报文
→ 手表回复命令 ACK
→ 手表上传新的位置或健康数据
→ 后端关联结果并标记操作完成
→ Web 自动刷新并展示结果
```

### 2.3 健康监测目标

- 只有设备在线、佩戴状态明确且处于佩戴中时，才主动发起心率和体温测量；
- 未佩戴时停止新的健康测量，但继续心跳、位置、取下报警和设备状态同步；
- 显示健康数据的新鲜度、测量异常和数据来源；
- 不将健康数据描述为医疗诊断结果。

### 2.4 安全事件目标

- 继续支持疑似跌倒功能；
- 不再把所有 `AL` 报文都直接解释为跌倒；
- 根据 `terminalStatus` 报警位识别跌倒类型；
- 告警具有去重、通知、确认和关闭状态。

---

## 3. 非目标

本期不承诺：

- 医疗诊断、疾病判断或自动救援；
- 血氧监测，协议 V3.0 没有对应上传命令；
- 在未完成真机验证前提供“立即测量血压”按钮；
- 小程序在后台长期运行定时器；
- 使用前端代码直接拼接完整设备报文；
- 同一设备同时执行多个相同类型的测量任务。

---

## 4. 现有实现评估

| 能力 | 当前实现 | 主要缺口 |
|---|---|---|
| TCP 下发 | `AdminDeviceController.sendCommand()` 可向在线连接写入报文 | 只返回 `sent`，没有 ACK/结果跟踪 |
| 协议构建 | `ProtocolParser.build()` 自动计算 `LEN` | 快捷动作尚未封装 |
| 位置接收 | `UD`、`UD2`、网络制式变体已入库 | 立即定位请求与新位置没有关联 |
| 健康接收 | `btemp2`、`bphrt` 已入库并 ACK | 无效值仍可能被展示，最新指标聚合有问题 |
| 在线状态 | `ONLINE/OFFLINE`、心跳时间、电量 | 没有佩戴状态和状态新鲜度 |
| 佩戴状态 | `LocationRecord` 仅保存原始 `terminalStatus` | 没有解析、去抖或设备级状态 |
| 跌倒 | `AL` 入位置表和 `fall_alerts`，Web/小程序可查询 | 所有 `AL` 都被视为跌倒；无处理状态、去重和推送 |
| Web 操作 | 文本输入框发送手写命令 | 不够友好，无法展示操作进度 |

## 5. 协议能力映射

### 5.1 快捷动作

| Web 动作 | 协议内容 | 前置条件 | ACK | 完成依据 |
|---|---|---|---|---|
| 立即定位 | `CR` | 设备在线 | `CR` | 请求后收到新的有效 `UD`/位置记录 |
| 测量心率 | `hrtstart,1` | 在线且已佩戴 | `hrtstart` | 请求后收到 `bphrt`，且心率有效 |
| 测量体温 | `bodytemp2` | 在线且已佩戴 | `bodytemp2` | 请求后收到 `btemp2`，且测量状态可解释 |
| 立即健康检测 | 顺序执行心率、体温单次测量 | 在线且已佩戴 | 分别 ACK | 两项完成或返回部分成功 |
| 刷新当前数据 | 无设备命令 | 无 | 无 | 重新查询后端数据 |

> 血压主动测量命令在现有协议中不明确。`bphrt` 是上传命令，`hrtstart,1` 可能只产生心率，血压字段可能为 `0`。完成真机验证前，不提供“立即测量血压”。

### 5.2 定时监测

| 监测项目 | 推荐实现 | 说明 |
|---|---|---|
| 位置 | 向设备下发 `UPLOAD,秒数` | 由手表自行定时上报；静止时可能不上报 |
| 心率 | 后端定时发送 `hrtstart,1` | 便于在未佩戴、离线时跳过；协议连续模式最短 300 秒，也可后续使用 |
| 体温 | 后端定时发送 `bodytemp2` | 便于按佩戴状态门控；后续可支持 `bodytemp` 或 `BTTIMESET` |
| 血压 | 仅接收设备主动上传 | 是否支持主动定时测量需厂商或真机确认 |
| 跌倒 | 设备本地持续检测并主动上报 `AL` | 后端负责分类、去重、通知和处置状态 |

## 6. 状态模型

### 6.1 设备状态

继续使用：

- `ONLINE`
- `OFFLINE`

主动下发前同时检查：

- `DeviceStatus == ONLINE`；
- `DeviceConnectionRegistry` 中存在活动连接；
- 最近心跳未超过配置的新鲜度阈值。

仅数据库中的 `ONLINE` 不足以证明连接仍然可用。

### 6.2 佩戴状态

新增 `WearStatus`：

- `WORN`：已佩戴；
- `NOT_WORN`：已取下；
- `UNKNOWN`：从未确认或状态已过期。

建议在 `Device` 增加：

- `wearStatus`；
- `wearStatusUpdatedAt`；
- `terminalStatusRaw`。

佩戴状态来自 `UD`、`UD2` 或 `AL` 中的 `terminalStatus`。需要先通过真机验证具体 Bit 掩码；项目内协议文档与此前整理版本存在相邻位含义冲突，不能未经验证直接固化。

### 6.3 佩戴状态去抖

- 连续两次相同状态，或状态持续 30–60 秒后确认切换；
- 状态超过配置时间未更新时转为 `UNKNOWN`；
- `NOT_WORN` 时停止新的健康测量；
- 恢复为 `WORN` 并稳定后，重新进入定时计划；
- 跌倒告警到达时使用报文自身状态为主，缓存佩戴状态只作辅助，不能直接丢弃告警。

### 6.4 动作状态

新增 `DeviceActionStatus`：

- `PENDING`
- `SENT`
- `ACKNOWLEDGED`
- `COMPLETED`
- `PARTIAL_SUCCESS`
- `SKIPPED_OFFLINE`
- `SKIPPED_NOT_WORN`
- `SKIPPED_WEAR_UNKNOWN`
- `SEND_FAILED`
- `ACK_TIMEOUT`
- `RESULT_TIMEOUT`
- `CANCELLED`

“写入 TCP”只对应 `SENT`，不能直接显示为“执行成功”。

### 6.5 数据新鲜度

Web 和小程序应区分：

- 最新值；
- 最新值测量时间；
- 数据是否过期；
- 设备是否在线；
- 佩戴状态是否可信。

建议由后端返回 `fresh/stale/unknown`，不要由不同前端各自维护规则。

## 7. 数据模型

### 7.1 `device_actions`

建议新增动作任务表：

```text
device_actions
├── id
├── deviceId
├── actionType
├── commandName
├── commandContent
├── status
├── requestedBy
├── requestedAt
├── sentAt
├── acknowledgedAt
├── completedAt
├── deadlineAt
├── resultRecordType
├── resultRecordId
├── failureReason
├── createdAt
└── updatedAt
```

协议没有请求 ID，因此采用以下关联约束：

- 同一设备、同一命令同一时间只允许一个未完成动作；
- ACK 按“设备编号 + 命令名 + 最近未完成动作”关联；
- 结果按“设备编号 + 数据类型 + `receivedAt >= sentAt` + 时间窗口”关联；
- 超时后到达的数据正常入库，但不自动覆盖已经关闭的旧动作。

### 7.2 `device_monitoring_policies`

```text
device_monitoring_policies
├── id
├── deviceId
├── enabled
├── locationIntervalSeconds
├── heartRateIntervalMinutes
├── temperatureIntervalMinutes
├── fallDetectionEnabled
├── fallSensitivity
├── wearStateRequired
├── desiredRevision
├── appliedRevision
├── lastAppliedAt
├── lastApplyError
├── createdAt
└── updatedAt
```

设备离线时保存期望策略，重连后再下发，不将离线直接视为永久失败。

### 7.3 健康记录

现有 `health_records` 建议增加：

- `measurementStatus`：`VALID`、`TOO_LOW`、`TOO_HIGH`、`INVALID`；
- `invalidReason`；
- `wearStatusAtMeasurement`；
- 可选 `deviceActionId`。

体温 `0/1` 和血压/心率 `0` 必须按协议转换为测量状态，不能直接显示为正常健康值。

### 7.4 跌倒事件

现有 `fall_alerts` 建议增加：

- `alarmType`；
- `terminalStatusRaw`；
- `deduplicationKey`；
- `status`：`PENDING`、`CONFIRMED`、`RESOLVED`、`FALSE_ALARM`；
- `confirmedAt`、`resolvedAt`；
- `handledBy`、`resolutionNote`。

只有确认跌倒报警位有效时才创建 `FALL` 事件。其他 `AL` 类型应分类保存，而不是显示为跌倒。

## 8. 后端服务设计

### 8.1 类型化设备动作

新增 `DeviceActionService`，职责包括：

1. 根据动作类型映射协议内容；
2. 检查设备在线和佩戴门禁；
3. 防止同类型动作并发；
4. 创建动作记录；
5. 使用 `ProtocolParser.build()` 构造报文；
6. 发送并更新为 `SENT`；
7. 处理 ACK、结果、超时和失败。

前端不得传入任意快捷动作报文。前端只传动作枚举，协议细节集中在后端。

### 8.2 ACK 处理

`DevicePacketDispatcher` 当前只对部分下行回复记录日志。需要把以下回复交给动作服务：

- `CR`
- `hrtstart`
- `bodytemp2`
- `bodytemp`
- `BTTIMESET`
- `UPLOAD`
- `FALLDOWN`
- `LSSET`

收到 ACK 后动作进入 `ACKNOWLEDGED`，但仍需等待业务结果才能进入 `COMPLETED`。

### 8.3 结果处理

- 保存新位置后，通知动作服务完成最近的 `LOCATE_NOW`；
- 保存有效 `bphrt` 后，完成最近的 `MEASURE_HEART_RATE`；
- 保存 `btemp2` 后，根据测量状态完成或标记异常结果；
- 组合健康检测由父动作聚合两个子动作结果。

### 8.4 定时任务

新增后台调度服务，周期扫描到期策略：

```text
策略到期
→ 检查在线连接
→ 检查佩戴状态及新鲜度
→ 检查同类动作是否正在执行
→ 创建单次测量动作
→ 记录跳过或执行结果
```

位置间隔配置优先由设备自身执行。健康测量初期由后端调度单次命令，便于佩戴门控和结果追踪。

## 9. API 设计

### 9.1 发起快捷动作

```http
POST /api/admin/devices/{deviceId}/actions
Content-Type: application/json

{
  "type": "LOCATE_NOW"
}
```

支持类型：

- `LOCATE_NOW`
- `MEASURE_HEART_RATE`
- `MEASURE_TEMPERATURE`
- `MEASURE_HEALTH`

成功接受返回 `202 Accepted`：

```json
{
  "id": 123,
  "type": "LOCATE_NOW",
  "status": "SENT",
  "requestedAt": "2026-08-11T10:00:00Z",
  "deadlineAt": "2026-08-11T10:01:00Z"
}
```

### 9.2 查询动作

```http
GET /api/admin/devices/{deviceId}/actions/{actionId}
GET /api/admin/devices/{deviceId}/actions?size=20
```

### 9.3 监测策略

```http
GET /api/admin/devices/{deviceId}/monitoring-policy
PUT /api/admin/devices/{deviceId}/monitoring-policy
```

### 9.4 健康概览

新增聚合响应，分别查询各指标最新有效记录：

```http
GET /api/admin/devices/{deviceId}/health-summary
```

返回心率、血压、体温各自的值、测量时间、状态和新鲜度，避免使用一条记录同时代表全部指标。

### 9.5 保留手写命令

继续保留：

```http
POST /api/admin/devices/{deviceId}/send-command
```

但 Web 将其移动到“高级工具”，明确提示：

> 手写命令只确认发送，不跟踪执行结果。错误命令可能改变设备配置，请仅由了解协议的管理员使用。

## 10. Web 交互设计

### 10.1 设备状态区

在设备基本信息顶部显示：

- 在线/离线；
- 已佩戴/未佩戴/未知；
- 佩戴状态更新时间；
- 电量；
- 最近心跳；
- 最新位置时间；
- 最新健康数据时间。

### 10.2 快捷操作区

按钮建议：

| 按钮 | 行为 | 禁用条件 |
|---|---|---|
| 立即定位 | 创建 `LOCATE_NOW` | 设备离线 |
| 测量心率 | 创建 `MEASURE_HEART_RATE` | 离线、未佩戴、佩戴未知/过期 |
| 测量体温 | 创建 `MEASURE_TEMPERATURE` | 离线、未佩戴、佩戴未知/过期 |
| 立即健康检测 | 顺序执行心率和体温 | 同上；真机验证完成后开放 |
| 刷新数据 | 重新加载设备、健康和位置 | 无 |

健康按钮因佩戴状态被禁用时显示具体原因，而不是只显示灰色。

### 10.3 操作反馈

操作后显示状态步骤：

```text
正在发送 → 设备已确认 → 等待测量/定位结果 → 已完成
```

错误提示应区分：

- 设备离线；
- 未佩戴；
- 佩戴状态未知；
- 命令发送失败；
- ACK 超时；
- 结果超时；
- 测量异常；
- 部分成功。

完成后自动刷新对应区域：

- 定位完成：刷新位置 Tab；
- 心率/体温完成：刷新健康概览和健康记录；
- 不因刷新失败把已经完成的设备动作标记为失败。

### 10.4 高级工具

现有手写输入框折叠到“高级指令”区域：

- 默认关闭；
- 保留原始报文回显；
- 增加二次确认；
- 后续记录管理员、命令内容和发送时间。

## 11. 定时策略建议

第一版默认值建议：

- 移动时位置上报：5 分钟；
- 心率：15–30 分钟；
- 体温：2–4 小时，或早/中/晚固定时间；
- Web 页面打开时自动刷新：30–60 秒；
- 佩戴状态超过 10–15 分钟未更新：转为 `UNKNOWN`；
- 单次定位结果超时：60–120 秒；
- 单次健康测量结果超时：120–180 秒。

这些是产品默认值，不是医学频率。正式值应结合设备耗电和真机表现调整。

## 12. 跌倒闭环

```text
设备 AL 上报
→ 校验 LEN 并保存原始报文
→ 解析 terminalStatus 报警位
→ 确认 FALL 类型并执行去重
→ 保存事件和关联位置
→ 回复设备 ACK
→ 通知绑定监护人
→ 监护人确认/标记误报
→ 记录处置结果
→ 关闭事件
```

注意：

- ACK 表示服务器收到，不表示监护人已经处理；
- 告警不得只依赖小程序 `onShow` 查询；
- 设备重发同一报警时不得无条件创建重复事件；
- 未佩戴状态可以降低可信度，但不能自动丢弃同一报文中的跌倒报警。

---

## 13. 错误处理和并发规则

- 同一设备同一动作类型只允许一个进行中任务；
- 组合健康检测内部顺序执行，避免同时占用传感器；
- 设备离线时，立即动作直接返回不可执行；
- 定时策略在离线时记录跳过，并在下一周期或重连后重试；
- ACK 丢失但结果已经到达时，可将动作直接完成并记录 `ackMissing=true`；
- ACK 到达但结果超时时，标记 `RESULT_TIMEOUT`；
- 设备上报无效测量时，保存原始记录并以测量异常结束，不伪装成正常值；
- TCP 写入成功不等于业务成功。

---

## 14. 安全与审计

- 快捷动作和手写命令仅限管理端认证用户；
- 后端维护动作类型到协议内容的白名单；
- 不允许前端通过快捷动作 API 传入任意命令内容；
- 记录操作人、设备、动作、参数、时间和结果；
- 危险的关机、重启、恢复出厂命令不加入普通快捷按钮；
- 健康数据和位置数据继续执行设备绑定/管理权限校验；
- 页面保留“仅供日常照护参考，不作为医疗诊断或紧急救援依据”。

## 15. 验收标准

### 15.1 快捷操作

- 在线设备可通过按钮完成立即定位、心率测量和体温测量；
- 前端不需要填写协议内容或计算 `LEN`；
- 离线或未佩戴时，健康按钮不可误触并说明原因；
- Web 能展示发送、ACK、等待结果、完成和超时状态；
- 新结果到达后自动刷新对应数据。

### 15.2 定时监测

- 定时健康任务只在在线且已佩戴时执行；
- 未佩戴或状态未知时有明确跳过记录；
- 位置继续按策略上报，页面能区分“手表位置”和“佩戴人位置”；
- 设备重连后能恢复尚未应用的监测策略。

### 15.3 健康数据

- 最新心率、血压和体温分别来自各自最新有效记录；
- 体温 `0/1`、血压心率 `0` 不作为正常值展示；
- 所有指标显示各自测量时间和数据新鲜度。

### 15.4 跌倒

- 只有跌倒状态位有效时才创建疑似跌倒事件；
- 重复报警不会产生无限重复事件；
- 告警具有服务端处理状态；
- 监护人可确认、标记误报和关闭事件。

## 16. 实施前必须确认

1. 真机确认 `terminalStatus` 中佩戴、静止、跌倒和取下报警的准确 Bit 掩码；
2. 确认 `hrtstart,1` 实际返回 `bphrt`，以及是否包含有效血压；
3. 确认 `bodytemp2` 的 ACK 与测量结果顺序、典型耗时和异常返回；
4. 确认 `CR` 后新位置通过哪个命令上报，以及静止状态下是否仍会上报；
5. 确认设备是否允许连续发送健康命令，或必须串行等待；
6. 确认 Web 快捷操作的管理员权限范围；
7. 确认跌倒通知优先采用微信订阅消息、短信还是两者并用。
